# agentic-support

[English](README.md) | **日本語**

[Google ADK](https://google.github.io/adk-docs/) の上に作ったサポート一次切り分けエージェント。Bedrock (Claude) か Gemini API のどちらでも動く — ADK はここではエージェントのフレームワークであって、モデルの提供元ではない。

曖昧な問い合わせを受け取って、どのテレメトリを取るか決め、それを読み、確度のラベルを明示した上で推定原因を返す — あるいは「分からない」と言う。

面白いのは答えのほうではない。**すべてのツール呼び出しが見えていて、すべての事実主張がツールの結果に辿れる**ことである。

後半にはモデルが1つも入っていない部分がある。[`queue_triage/`](queue_triage/) はキュー全体を「各チケットがどれだけ安く閉じられそうか」で並べる。つまり**どのチケットを最初に開くか**はエージェントが関わる前に決まっている — 決定的に、そしてすべてのスコアが「発火したルールのリスト」として説明可能な形で。[エージェントの前: どのチケットから](#エージェントの前-どのチケットから) 参照。

## なぜ

私は仕事としてクラウドのサポートチケットを扱っている。チケットの最初の10分はほぼ毎回同じ形をしている: 顧客がどのリソースを指しているのか特定し、そのメトリクスを見て、ログを読む価値があるか判断し、仮説を立てる。機械的で、まさにエージェントが役に立つべき場所である。

そういうエージェントを顧客の前で使い物にならなくする失敗の仕方は、**自信を持った捏造**である — テレメトリのどこにもそう書いていないのに「あなたの Lambda はスロットリングされています」と言うこと。なのでここでの設計上の制約は「役に立て」より厳しい:

- 顧客のシステムに関する事実主張は、すべてツールの結果から来なければならない。
- ツールがチケットと矛盾していたら、辻褄を合わせずに矛盾を報告する。
- チケットがリソースを名指していなかったら、質問する。推測しない。

最後のものは見た目より重要である。顧客がどの関数を指していたか推測するエージェントは、いずれ**間違ったシステムを正しく診断して、信じられる**。

## 仕組み

```
チケット本文
    │
    ▼
┌──────────────────────────────┐
│ intake_classifier            │  ツールなし、構造化出力:
│  テキストのみ、テレメトリなし │  category / resource / urgency
└──────────┬───────────────────┘
           ▼
     ┌───────────────┐   調べるものが無い
     │ pipeline gate │──────────────────────▶ リソースを聞き返す、
     └───────┬───────┘                        あるいはドキュメントから答える
             │ リソースが名指されている
             ▼
┌──────────────────────────────┐
│ triage_agent (LlmAgent)      │
│  根拠のルール +               │
│  切り分け手順                 │
└──────────┬───────────────────┘
           │ ツール呼び出しループ
     ┌─────┴──────┐
     ▼            ▼
get_function   get_recent
_metrics       _logs
     │            │
     └─────┬──────┘
           ▼
     policy.py          ← 順序と not_found のルールはここにある
           │
           ▼
    mock_infra.py
  （顧客自身の API の
    代わり）
```

intake が先に、安く走る: テキストのみ、誤用できるツールが無く、出力はラベルと照合できる固定の enum。triage が高い段で、gate がチケットがそれに値するかを決める。2つを分けておくと、**誤ルーティングは誤ルーティングとして現れる** — 後になって「自信を持って間違った診断」として出てくるのではなく。

エージェントには、まずメトリクスに手を伸ばし、メトリクスが実際に何かおかしいと示唆した**場合にのみ**ログを取れと指示している。安い信号を高い信号の前に — 人間のオンコールが使うのと同じ順序であり、何も壊れていない大多数のチケットではトークンコストを抑えるはずである。まだそうなっていない。[既知の穴](#測定を始めさせた穴) を参照。

`mock_infra.py` は意図的に、**背後のシステムが何であるかを知る唯一のファイル**である。実際の案件ではあの2つの関数が可観測性バックエンド、CMDB、チケットシステムを呼ぶことになり、それぞれが独自の認証とネットワーク境界の向こうにいる。本物の統合が入るときに変わるのはそのファイルだけで、エージェント層は変わらない。

このファイルは両方の形のデータを意図的に持っている:

- **構造化** — 呼び出し回数、エラー率、p99 レイテンシ
- **非構造化** — 生のログ行。エラーが繰り返されてノイズになるケースを含む

後で検索が対処しなければならないのは、汚いほうだから。

### 試す価値のあるもの

| チケット | 何を試すか |
|---|---|
| `"checkout-api is slow this morning"` | メトリクス → ログ → 原因（遅さではなく DynamoDB への接続タイムアウト） |
| `"notifications aren't going out"` | リソースが名指されていない — 推測せず聞き返すべき |
| `"invoice-batch is throwing errors"` | テレメトリは正常 — 前提そのものに反論すべき |
| `"payment-api is down"` | 存在しない関数 — `not_found` の扱い |

3番目が本当の試験である。愛想よくしたいモデルは、**あると言われたから** `invoice-batch` に問題を見つける。

### 測定を始めさせた穴

`invoice-batch` のチケットで、エージェントは結論を正しく出した — テレメトリは正常、捏造された障害も無し — が、**ログを取ってしまった**。指示は、メトリクスが問題を示唆したときだけそうしろと言っていた。根拠付けは守られ、コストの順序は守られなかった。**指示は制御面ではない。**

これは今 [`policy.py`](support_agent/policy.py) で強制されているが、この修正が何を買ったのかは正確に言う価値がある。エージェントは今もログ呼び出しを**試みて**、`skipped_by_policy` を受け取り、それからメトリクスだけで答える。根拠付けは守られ答えも正しいが、**リクエスト自体は出ているので呼び出し回数は減っていない**。コストを削るのに必要だったのはツールの gate ではなく intake の gate だった — そしてその区別が見えたのは、2つを別々に測っていたからである。

## モデル

プロバイダは2つ。どの認証情報があるかで選ばれ、段ごとに上書きできる:

```bash
SUPPORT_AGENT_BACKEND=bedrock     # triage は Claude Sonnet 5、intake は Haiku 4.5
SUPPORT_AGENT_BACKEND=gemini      # gemini-3.8-flash
SUPPORT_AGENT_MODEL=<model>            # triage のみ
SUPPORT_AGENT_CLASSIFIER_MODEL=<model> # intake のみ
```

intake と triage を別々に設定できるのは意図的で、分類は出力の形が固定された安いタスクであり、triage が必要とするモデルを必要としない。

2つ目のプロバイダは、移植性のための移植ではなかった。Gemini の無料枠はモデルごとに1日20リクエストで、スイート1回の実行にはそれ以上必要になる。つまり測定ハーネスをおよそ1日1回しか回せない — ハーネスと呼べるかどうかの状態だった。Bedrock がその天井を外して、以下の数字が再現可能になった。

移植は同時に、**設計がどれだけ1つのベンダーに漏れているかの一番速い監査**でもあった。1つ漏れていた: intake は urgency を `ge=1, le=4` の整数として宣言していて、Gemini はそれを受け付け、Bedrock は端的に拒否した — その構造化出力スキーマでは整数に `minimum`/`maximum` を付けられない。文字列の enum に置き換えたのは移植可能で**かつ良い**。値が自分の意味を持ち、[`sla.py`](support_agent/sla.py) の urgency のレベルと厳密に一致するので、AI の段とポリシーの段の間に変換表が必要なくなる。2つの enum が同期し続けることをテストが主張している。ずれたときの失敗は、誰も検証していない値から計算された期限だからである。

毎回の実行で解決済みのモデル ID を表示する。この行があるのは、`.env` に残った古い `SUPPORT_AGENT_MODEL` が黙って backend を上書きして、スイート1回ぶんを間違ったプロバイダに送り、そこで無料枠の上限で死んだのに、**出力のどこにもどのモデルが使われたか書いていなかった**からである。

`.env` の `GOOGLE_GENAI_USE_VERTEXAI=TRUE` は、同じエージェントを Gemini API の代わりに Vertex AI に対して走らせる。

## AI ではない部分

診断が上手くて回答が遅いエージェントは、結局コミットメントを外している。なので2つのモジュールは意図的に、モデルの入らない素のコードである。

**[`sla.py`](support_agent/sla.py)** — 影響度 × 緊急度 → P1〜P4、そこから営業時間ベースの期限。影響度を顧客の自己申告の緊急度より重く扱っている: 1テナントが「重大」と言っているものは P2、共有コンポーネントが全員に対して劣化していれば緊急度が中でも同じく P2。自己申告の緊急度だけだと、**一番声の大きいチケットが一番重要**になってしまう。

バグが住んでいるのは時計のほうである。9:30 に開いて 18:15 に閉じるデスクにとって、経過した実時間は間違った尺度である: 金曜17時に上がった P1 は月曜の朝時点で違反ではない。なので `BusinessCalendar` は開いている分だけを数え、週末・日本の祝日・12/29〜1/3 の休業で止まる。**幻の違反は測定しないより悪い**。誰かが午前中を使って「その数字は間違っている」と説明することになるからである。

その中の2つの判断は意図的で、レビューで議論する価値がある:

- `escalate()` は優先度を上げるが、期限は**再計算しない**。すでに顧客にしたコミットメントは、社内の再分類が短縮していいものではない。
- 祝日リストはハードコードされていて、コード中のコメントが「これは権威あるフィードに置き換えられるべきプレースホルダである」と言っている。ハードコードされたカレンダーデータは**予定どおりに間違いになる** — ただしいつ間違いになったかは教えてくれない。

**[`quality.py`](support_agent/quality.py)** — すでに対応済みのチケットをレビューして、重大度別に findings を出す: `BREACH`（目標を外した）、`PROCESS`（正当な理由なくエスカレーションした、あるいは誰もエスカレーションしなかった P1）、`HYGIENE`（リソースが特定されていない、根拠が引用されていない）。スコアカードは SLA 達成率、再オープン率、根拠提示率を集計する。

重要なのは分母である。初回応答の達成率は**バッチ全体**を数え、初回応答が一度も無かったチケットも含める。除外すると最悪のチケットが数字を改善できてしまい、それが指標が逆方向を指し始める仕組みである。

## エージェントの前: どのチケットから

[`queue_triage/`](queue_triage/) は、上の全部より前に来る問いに答える。未対応40件、自分は1人、そしてどれが20分で終わる回答でどれが午後を丸ごと食うかについて信号が無い。古い順に並べれば最古が先頭になり、重大度で並べれば顧客が埋めたフィールドを信用することになる。

これは意図的にエージェントではない。モデルもネットワークも無く、すべてのスコアが**重み付きで発火したルールのリスト**である:

```bash
uv run python -m queue_triage queue --explain
```

```

       +3 waited-24d  (aging, order only)

      !   known-hard example: The phrase "credit card" made an earlier version of
          the ruleset score this as a credits question worth +6...
```

2つ目が、説明が飾りではない理由である。`credit card` は `credit` を含むので、初期版はクレジットカードの不正利用の申し立てを「よくあるクレジット残高の質問」として採点し、quick win に並べていた。**シグナル単位の内訳を読んで見つかった**。テストは、私が先にそれを思いついていた場合にしか見つけられなかった。

**2つのものが意図的にスコアの外にある。** チケットがどれだけ待っているか、そしてそれがキューが提示すべきでない形のものかどうか。

待ち時間は公平性の制約であって、工数についての根拠ではない。チケットは週1点、上限4点まで加算される。これは2週間前のチケットを、1〜2点高かった当日のチケットより前に出すには十分で、定型返信と障害の間の差を年齢が覆すには不十分である — 上限が無いとこれは先着順に崩壊し、それはランカーが改善するために存在しているものそのものである。このボーナスは `Verdict.score` ではなく `Verdict.adjustments` に入るので、**キューに座っているだけでチケットが `quick-win` になることはない**。ソートはチケット ID の前に作成日にフォールバックするので、同じくらい安いチケットの中では一番長く待っているものが先に提示される。

除外はもう1つの層である: 返金と請求調整はペナルティではなく**落とす**。ペナルティは「これは高そうだ」と言って画面の下部にチケットを残すが、それは「他人のワークフロー」の意味ではない — その数字がいくつであっても、スコアではそれを表現できない。落としたチケットは件数と名前を stderr に出す（`dropped 3: 3x refund-request`）。黙って消えたチケットは壊れたクエリと区別がつかないからで、`--keep-excluded` で戻せる。

**どちらの層も測定経路には触っていない。** `evals/rank.py` はキューが隠すものも含めて全チケットを採点し、aging を切って走る — そして [そうであり続けることを保つテスト](tests/test_rank_eval.py) がある。これは両方向に効く: 敵対的ケースのうち2件は返金依頼で、この集合の中で減衰機構の一番鋭い試験になっている。そしてラベル付きチケットは偶然「古いものほど簡単」な順に書かれているので、aging を `score` に入れればルールセットが良くなっていないのに一致率の数字が上がっていた。両方の層を足して eval は**ちょうど何も動かなかった**、というのがその要点である。

**なぜ分類器ではなくルールセットか。** モデルのほうがおそらく上手く並べる。同時にチケット1件あたり1呼び出しかかり、1件あたり1秒かかり、「なぜこれが先頭なのか」に監査可能な履歴ではなく**もっともらしい一文**で答える。だいたい合っていれば十分で、人間が別の行を選べば無料で上書きできるランキングにとって、決定的な版のほうが良い取引である。[ルールセットは YAML ファイル](queue_triage/rulesets/cloud_support.yaml) なので、重みを変えるのはコード変更ではない。

**部品。** クエリのコンパイラは AST で止まり（[`query.py`](queue_triage/query.py)）、バックエンド固有のエンコードは [`emit.py`](queue_triage/emit.py) にある。この分割が設計の全部である: 実在する検索 API はどれも、入れ子のブール木をどうエンコードしてほしいかに癖があり、その癖は**エラーではなくもっともらしい間違った答え**を返す。名指しする価値があるのは、引用符の無い複数語の値がしばしばトークン化されて OR されることで、`body:missing credits` は `body:credits` より**多く**マッチする — 絞り込みのように読めるフィルタが広げている。間に AST があれば、パーサの仕事は1つになり、各バックエンドの奇妙さは1関数になる。バックエンドは2メソッドで、同梱のものは YAML ファイルを読むので、上の全部が認証情報なしで動く。

### ランキングの eval が見つけたもの

```bash
uv run python -m evals.rank --signals --ablate
```

正解データは観測された処理時間ではなく**手で置いた事前分布**であり、それが主張できる範囲を縛る: 順位の一致と ablation の差分は言えるが、正解率は言えない。ハーネスは正解率の数字を1つも表示せず、[表示し始めないことをテストが主張している](tests/test_rank_eval.py)。

ラベル付き32チケットでの現在の数字 — Spearman **+0.845**、安いチケットが難しいチケットより下に並んだことは無し、上位5件は全部本当に安い。しかし面白かった出力は診断のほうで、実在する欠陥を3つ見つけた。

**2つのシグナルが一度も発火していなかった。しかもそれが「単に該当しなかった2つ」と見分けがつかなかった。** `short-subject` と `long-subject` は件名の長さを `^.{0,45}$` で測る。これが改行で連結した全フィールドに対して走っていて、`.` は改行を越えないのでパターンは**絶対にマッチしない**。両方とも書かれた日から死んだコードだった。修正はシグナルに `scope` を持たせることで、フィールドの中身ではなく形を測るものには今これが必須である。`short-subject` は発火0回から16回になった。

**1件のチケットが、この集合の「ひどく逆転したペア」を全部生んでいた。** 上の誤検知を直した後もまだ +4 で採点されていたクレジットカード不正利用の申し立てである。不正利用の疑いは請求の質問のように読めるが、そうではない — 書いてきている人がアカウントの持ち主でない可能性がある。`suspected-fraud` シグナルを足して、ひどく逆転したペアは4件から0件に、Spearman は +0.810 から +0.845 になった。

**文脈による減衰の ablation がちょうど0で返ってきて、しかも原因は機構のほうではなかった。** 減衰は、請求系のシグナルが既に発火しているときにサービス名のペナルティを半分にする。請求に異議のある顧客は、自分が驚いた明細項目の名前を出すからである。これが「価値なし」と測定されたのは、**データセットにそれが存在する理由となるケースの例が無かった**からだった — カバーしているつもりだった1件は NAT ゲートウェイを名指していて、それは同じ理由でネットワークのパターンから既に外されていた。今は Direct Connect のポート時間料金を名指す請求チケットがそれをカバーしている。正直な数字は今も小さい（Spearman +0.003、チケット1件ぶん）が、切り上げて主張にせず、そのまま報告している。

シグナル単位のレポートは、1つだけ残せるとしたら残す検査である: 各シグナルについて、それが発火するチケットのラベル平均と、発火しないチケットの平均を比べる。**正の重みなのにそのチケットが平均より時間がかかっているなら符号が逆**で、大きさをいくら調整しても直らない。発火3回未満ではその判定を拒否する。1件が平均の上下どちらに落ちるかはコイン投げであって、根拠ではないからである。

## CI

[CI](.github/workflows/ci.yml) は push ごとに決定的な半分を走らせる: 優先度マトリクス、営業時間の時計、スコアカード、eval ハーネス自身の採点ロジック、そして `queue_triage` の全部（ランキングの eval を含む）。認証情報なし、モデル呼び出しなし、ぶれなし。

ランキングの eval が CI に属するのは、まさにそこにモデルが入っていないからである。固定のデータセットを固定のルールに通すので、数字の変化はルールセットの変化であり、スイートは落ちる価値のある2つのことで落ちる: **一度も発火しないシグナル**と、**重みがラベルと矛盾しているシグナル**。

エージェントの eval は CI に**入っていない**。金がかかり、キーが必要で、非決定的である。push ごとに配線すればキーが漏れるか、コミットと無関係な理由でビルドが赤くなるかのどちらかで、間違った理由で赤いビルドは無視されるようになる。これらは `--repeat` を付けて必要なときに走らせ、その数字は実行回数を添えてこの README に入る。

ハーネス自身の検査にもテストがある。これは心配しすぎではない: **abstention の検査は一度壊れた状態で出荷された**。`?` を探していたので、正しい日本語の聞き返しを全部失敗させていた。日本語の疑問文は普通に「。」で終わるからである。スイートは動いているエージェントを壊れていると報告していた — eval の失敗の仕方として唯一許容できないものである。正しかったコードを直しに行かせるからである。

## 測る

```bash
uv run python -m evals.run                     # スイート全体、1回
uv run python -m evals.run --only vague-en-04  # 1チケットだけ
uv run python -m evals.run --repeat 5          # 何が間欠的かも報告する
uv run python -m evals.run --json out.json     # 機械可読
```

[`evals/tickets.yaml`](evals/tickets.yaml) にラベル付きチケットが入っている。各件が実行の**前**に、正しい答えがどう見えるかを記録している: 期待される intake のカテゴリ、triage が呼ぶべき/呼ぶべきでないツール、エージェントが機構を捏造した証拠になる部分文字列、そして正しい答えが診断ではなく質問かどうか。正解が「何も壊れていない」や「分からない」であるケースは一級市民である — 愛想のよいエージェントが落とすのはそれらだから。

judge モデルは1つも使っていない。すべての検査は書き下された期待値に対する決定的な比較なので、退行は「意見が変わった」ではなく「数字が動いた」になる。採点している軸:

| 軸 | 何を捕まえるか |
|---|---|
| intake のカテゴリ / リソース抽出 | 間違った場所にルーティングされたチケット |
| ツールの規律 | 起きるべきでなかった呼び出し、およびその逆 |
| 根拠付けの代理指標 | どのツールも報告していない機構を主張している |
| 棄権 | 聞き返すべきときに診断している |
| 回答の言語 | 日本語のチケットに英語で答えている |
| チケットあたりのトークンとツール呼び出し | 上のコスト |

### 1回の実行は測定ではない

エージェントは非決定的なので、1回の実行から出した合格率は**標本数1をプロパティとして提示したもの**である。`--repeat` はスイートを N 回走らせて、検査を**常に通る**ものと**時々通る**ものに分ける。この2つには別の対応が必要だから: 毎回落ちる検査は原因が既知の欠陥であり、5回に1回落ちる検査は、ハーネスが「間欠的である」と教えてくれない限り「再現できませんでした」で閉じる欠陥である。

間欠的な失敗も実行を失敗させる。根拠付けの検査が5回中4回通ったら緑になるスイートは、スイートが無いより悪い。

### 見つかったもの

3つの欠陥。どれもアドホックなテストでは見えなかった。

**リソースを推測していた。** `notifications aren't going out` に対して分類器は正しかった — `function_name: null`、`needs_telemetry: false`。生のチケットに対して走った triage は `notify-fanout` を推測して、そのメトリクスを取ってしまった。推測するなという指示は既にあった。それが**ツールがあり、もっともらしい候補があり、答えを欲しがっている顧客がいる**ことに負けた。

**隣のものに置き換えていた。** 存在しない `payment-api` について聞かれたエージェントは、`not_found` のペイロードで `known_functions: [checkout-api, …]` を受け取り、`checkout-api` を選んで、その DynamoDB のタイムアウトを答えとして報告した — **誰も聞いていないシステムの正しい診断**を、自信を持って。原因は親切なエラーメッセージだった。

**間違った言語で答えていた。** 指示は「チケットが書かれた言語で答えよ」と言っていた。5回の実行でそれが守られたのは4回で、2回は `invoice-batch` についての英語のチケットに**ドイツ語**で答えた。チケットにドイツ語の要素は無い — モデルが単に流れただけである。そして顧客が書いていない言語で返信するサポートデスクは、診断がどれだけ良くても失敗している。

これは二重に隠れていた。捕まえるべき検査が「返信が日本語でないこと」だけを見ていたからである。ドイツ語は日本語ではないので緑で採点された。検査を直したら、次の実行でこの欠陥が出てきた。

### その結果として変えたこと

3つの修正はすべて、制約を**モデルが手を伸ばせない場所**に移している:

- [`policy.py`](support_agent/policy.py) は、ログ取得をメトリクスが正常範囲外であることに条件づけ、`not_found` の結果から有効な名前のリストを剥がす。エージェントには**何を持っていないか**を伝え、代わりに何が持てたかは伝えない。
- [`pipeline.py`](support_agent/pipeline.py) は分類器の判断を拘束力のあるものにする: intake が「調べるものは無い」と言えば、triage は走らない。
- `pipeline.triage_prompt()` はチケットの文字種から返信言語を決めて（2行の関数）、それをメッセージ内で命令形で述べる。モデルはもう推論しない。推論していたことがばらつきの出所だったから。

`mock_infra.py` は顧客のシステムの忠実な代役のままで、以上のどれも知らない。

同じ教訓はパターンにも当てはまる、個別のケースだけでなく: **これらはどれも指示の中の一文として始まっていて、欠陥が測定されたときその一文はすでに存在していた**。従順さは、モデルが元々どれだけ従いたかったかに比例して得られる。

### エージェントについて間違っていた測定

このスイートが生んだ一番有用なものは、**スイート自身についての発見**だった。

上の修正の後、5回連続の実行が 97〜100% を出し、3チケットにまたがって根拠付けの間欠的失敗が4件あった。その失敗は、エージェントが時々機構を捏造しているように見えた。数えるのではなく読んでみたら、別のものが見えた。実行からそのまま:

> **No evidence of** throttling, cold starts, or deployment changes — none of
> those appeared in the metrics or logs, so I'm not listing them as contributing
> factors.

> 追加で確認したい点があれば、DynamoDB側のテーブルメトリクス（スロットリングや
> キャパシティ状況など）も合わせて調査することをお勧めします。

1つ目はエージェントが**何を除外したか**を述べている。2つ目は次の一手として DynamoDB 側のスロットリングのメトリクスを確認することを勧めていて、しかも自分のツールではそれが見えないと言っている。どちらもサポートエンジニアに望む振る舞いで、どちらも**捏造として採点されていた** — 検査が部分文字列テストで、`"throttl" in answer` では**スロットリングが原因**と**スロットリングの証拠なし**を区別できないからである。

つまり答えが良くなっているのにスイートの数字が下がった。それは指標の間違い方として一番高くつく。**改善を巻き戻す方向に議論が進む**からで、しかも合格率だけを読んでいる限り見えない。

修正は、判断の単位を答え全体から**節**に移した: 機構が捏造とみなされるのは、それを含む節が因果を主張し、かつその機構を否定していないときだけである。日本語には2周目が必要だった。日本語の否定は節末に来るので、言及からかなり後に着地する — 「…を直接示すログはないため、根本原因の特定はここまでとし」は、同じ息で機構を否定しつつ「根本原因」と言っている。

保存済みの実行を修正後の検査で再採点すると（新しいモデル呼び出しは0回。答えはすでに保存されていた）、根拠付けの検査は **95/95** が緑になり、そして**先に見つかった本物の失敗は今も落ちる**。そこが重要な部分である:

> **Probable root cause:** Connectivity or throttling issues between
> `checkout-api` and the DynamoDB endpoint in `ap-northeast-1`

スロットリングは何も報告していない。これは捏造であり、今も捕まる。両方の文字列は [`tests/test_eval_checks.py`](tests/test_eval_checks.py) のテストケースになっていて、テストを通すために書いたものではなく実行からそのまま取ってきたものである。

関連して記録する価値のある結果がある。スロットリングの失敗が最初に現れたとき、私の修正は triage の指示にその例を名指しするルールを足すことだった — *「Connectivity or throttling issues」はスロットリングを主張している*。5回の実行で測ったら、スロットリングへの言及は**増えた**、減らなかった。**使ってほしくない語を名指しすると、その語が手元に来る。** 言い換えたルールが実際に生んだのは、あの明示的な「no evidence of throttling, cold starts, or deployment changes」の段落だった — 壊れた検査がその後で罰していた改善である。

### 正直なステータス

決定的なものはすべて — 優先度マトリクス、営業時間の時計、品質スコアカード、ハーネス自身の採点ロジック — 単体テストがあり、push ごとに [CI](.github/workflows/ci.yml) で走る。

以下のエージェントの数字は Bedrock（triage が Claude Sonnet 5、intake が Haiku 4.5）での5回連続実行のものである。1回の実行では主張を支えられないので、実行回数を添えてある:

| | 5回の結果 |
|---|---|
| 通った検査 | 4回で 87/87、1回で 86/87 |
| 合格率 | 最良 100%、最悪 99% |
| チケットあたりトークン | 約3,950（両段合計） |
| チケットあたりツール呼び出し | 1.00 |
| 言語の正しさ | 修正後 5/5、修正前 3/5 |
| 捏造された原因 | 根拠付け検査 0/95 が失敗 |

この集合で唯一落ちたのは、abstention の検査が**平叙文の形で書かれた依頼**を取り落としたものだった — "I need you to confirm the exact function name" に疑問の語は含まれていない。マーカーのリストを直し、その実行の文字列をテストケースにした。5回の保存済み実行を修正後の検査で再採点すると回答レベルの検査は **195/195** になるが、これは「スイートが5回連続で通る」と同じ主張ではないので、そう読めるようには書いていない: **答えは固定されていて、変わったのは採点だけ**である。

生の結果は [`evals/stability.json`](evals/stability.json) に commit してある — すべての答え、すべての検査、すべての実行 — なので上の数字は信じるのではなく再計算できる。

これが教えてくれない2つのこと。スイートはモックのバックエンドに対する9チケットなので、測っているのは**エージェントの規律**であって実際のテレメトリの難しさではない。そして `must_mention` のグループは部分文字列マッチなので、モデルが言い換えるたびに広げないといけない — ある実行は「not found」を "no function with that exact name exists" と表現して、取り落としとして採点された。それが judge モデルを拒否することの継続的なコストであり、2つのコストのうち安いほうである: judge は毎回新しい意見を形成し、するとスイート自身の判定がぶれ始める。

## この先

複雑さに見合う順に、だいたい:

- **本物の祝日フィード** — `sla.py` は日本の祝日をハードコードしていて、コメントでそう言っている。ハードコードされたカレンダーデータは予定どおりに間違いになり、それを知らせてこない。
- **runbook に対する検索** — 上のログ行は、前に見たことのある人には見覚えがある。その知識は runbook にあり、重みの中にはない。
- **委譲** — triage と復旧を分けて、修正を提案するエージェントが何が壊れているかを決めたエージェントと同一でないようにする。
- **クラスタからの FAQ 候補** — 繰り返し来るチケットはドキュメントの負債である。intake のカテゴリで時系列にまとめるのが、どのドキュメントページが足りないかを見る一番安い方法である。
